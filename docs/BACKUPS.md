# Резервные копии базы на компьютер Директора

Цель: если база на сервере удалится (например, у бесплатной базы Render истёк срок) или сервер сломается, все данные CRM остаются у Директора и восстанавливаются.

## Как это устроено

- Сервер собирает **полную копию**: все таблицы, загруженные файлы (договоры, чеки, аватары) и ключи, нужные для расшифровки данных.
- Копия сразу **шифруется открытым ключом Директора** (RSA-4096 + AES-256-GCM). Закрытого ключа на сервере нет. Поэтому прочитать копию не могут ни сервер, ни хостинг, ни тот, кто перехватит файл или токен.
- Копия попадает на компьютер Директора двумя способами:
  1. **Автоматически.** Программа-агент на компьютере скачивает копию каждый день в 13:00 и 19:00. Если компьютер был выключен, скачивание запускается при следующей возможности. Хранятся последние 60 копий.
  2. **Вручную.** В CRM Директор запрашивает код `backup.export` и скачивает файл: `GET /backups/export`.
- Если копия не скачивалась **48 часов**, Директорам приходит письмо-напоминание.
- В копию **не входят** активные сессии и одноразовые коды. После восстановления все просто входят заново.

Файл копии: `uzz-crm-backup-ГГГГММДД-ЧЧММСС.uzzbak`.

## Настройка (один раз, делает разработчик вместе с Директором)

### 1. Ключи шифрования

На компьютере разработчика в папке проекта:

```bash
BACKUP_KEY_PASSPHRASE='придумайте-длинную-фразу-не-короче-16-символов' npm run backup:keygen -- ./backup-keys
```

- `backup-keys/private.pem` — **закрытый ключ**. Передайте Директору на флешке и сохраните вторую копию в сейфе. Его **нельзя** класть на сервер, в git или отправлять в мессенджер. После передачи удалите ключ с компьютера разработчика.
- **Фразу-пароль** запишите отдельно от ключа, например на бумаге в сейфе.
- Без ключа **и** фразы открыть ни одну копию невозможно. Если потерять оба, копии бесполезны.
- Команда напечатает длинное значение `BACKUP_PUBLIC_KEY`, его нужно вписать на сервер.

### 2. Токен агента

```bash
npm run backup:agent-token
```

- `TOKEN` вводится при установке агента на компьютер Директора.
- `BACKUP_AGENT_TOKEN_SHA256` вписывается на сервер.

### 3. Сервер (Render → сервис → Environment)

- `BACKUP_PUBLIC_KEY` — значение из шага 1.
- `BACKUP_AGENT_TOKEN_SHA256` — значение из шага 2.

Сохраните настройки, сервис перезапустится. Проверка: `GET /backups/status` под Директором должен вернуть `configured: true` и `agentConfigured: true`.

### 4. Агент на компьютере Директора

Скопируйте на компьютер папку `backup-agent` из репозитория.

**macOS.** Откройте «Терминал» и выполните:

```bash
bash ~/Downloads/backup-agent/macos/install.sh
```

Программа спросит адрес сервера (`https://...onrender.com`) и токен. Копии сохраняются в папку `~/UZZ-CRM-Backups`, журнал пишется в `~/Library/Application Support/UZZ-CRM-Backup/backup.log`. Если скачать не удалось, появится уведомление.

**Windows.** Нажмите правой кнопкой на `backup-agent\windows\install.ps1` → «Выполнить с помощью PowerShell». Или выполните:

```bash
powershell -ExecutionPolicy Bypass -File backup-agent\windows\install.ps1
```

Копии сохраняются в `C:\Users\<имя>\UZZ-CRM-Backups`. Токен хранится зашифрованным средствами Windows и доступен только этому пользователю.

Удаление агента: `uninstall.sh` / `uninstall.ps1`. Скачанные копии при удалении остаются.

## Проверка копии

Проверяйте раз в месяц: копия, которую ни разу не открывали, может оказаться бесполезной.

```bash
BACKUP_KEY_PASSPHRASE='...' npm run backup:inspect -- ~/UZZ-CRM-Backups/uzz-crm-backup-....uzzbak ./private.pem
```

Команда покажет дату копии и количество записей по таблицам. Сами данные она не выводит.

## Восстановление после потери базы

1. Создайте **новую пустую** базу PostgreSQL (новая база на Render, Neon или локальная).
2. Примените миграции:
   ```bash
   DATABASE_URL='<адрес новой базы>' npx prisma migrate deploy
   ```
3. Восстановите данные из **последней** копии:
   ```bash
   DATABASE_URL='<адрес новой базы>' FILE_STORAGE_DIR=./storage BACKUP_KEY_PASSPHRASE='...' npm run backup:restore -- <файл.uzzbak> ./private.pem ./restored-keys.env
   ```
   - В базу, где уже есть данные, восстановление **не выполняется**: перезаписать рабочие данные случайно нельзя.
   - В `restored-keys.env` записываются `ENCRYPTION_KEY_*` и `BLIND_INDEX_KEY_V1` из копии.
4. На сервере:
   - укажите `DATABASE_URL` новой базы;
   - замените `ENCRYPTION_KEY_V1` и `BLIND_INDEX_KEY_V1` значениями из `restored-keys.env`. **Без этого данные не расшифруются.**
   - Затем **удалите** `restored-keys.env`.
5. Загруженные файлы (договоры, чеки) восстанавливаются в `FILE_STORAGE_DIR`. На бесплатном Render диск временный, поэтому файлы после перезапуска снова пропадут. Для постоянного хранения файлов нужен платный диск или облачное хранилище.
6. Все пользователи входят заново: пароль и код из письма.

Данные, созданные после последней копии, восстановить нельзя. Поэтому агент скачивает копию дважды в день.

## Безопасность

| Угроза | Защита |
|---|---|
| Украли файл копии | Файл зашифрован, без закрытого ключа и фразы не читается |
| Украли токен агента | Токен даёт только зашифрованный файл. Замените токен: `npm run backup:agent-token`, новое значение на сервер и в агент |
| Украли закрытый ключ | Ключ сам защищён фразой-паролем. Создайте новые ключи и замените `BACKUP_PUBLIC_KEY`. Старые копии открываются только старым ключом |
| Файл подменили или повредили | Проверка целостности (GCM): такая копия не откроется |
| Кто-то скачивает копии | Каждое скачивание и каждая неудачная попытка пишутся в журнал аудита (`BACKUP_EXPORTED`, `BACKUP_AGENT_AUTH_FAILED`) |
